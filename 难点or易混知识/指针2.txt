p->member   // 等价于 (*p).member，例如
typedef struct node {
    int value;
    struct node *next;
} node;
Node *p;
p=head->next;即p=(*head).next，因为这里的next类型是node *，所以->直接就是为那个的地址

每当我们想要更新一个变量的值时，我们需要传递一个指向它的指针，所以如果想改变指针的值，则需要传递指向指针的指针即例如Node **a

const char * 是一个指向字符常量的指针，即指针本身可以改变（指向其他地址），但不能通过这个指针修改它所指向的字符。
拆解理解
    char *：指针，指向一个字符（或字符数组，即字符串）。
    加上 const 修饰 char：表示指针指向的字符是只读的。
C 语言允许指针和整数比较，主要因为：
    空指针比较：ptr == NULL，其中 NULL 是整数常量 0。

1. 数字字符 '0' 与整数 0 完全不同
字符 '0' 的 ASCII 码是 48（十进制），所以在代码中写 '0' 等价于整数 48。
整数常量 0 就是数值 0。
所以当你写 if (check_range(*password, 0, 9)) 时，实际上是在检查字符的 ASCII 是否在 0~9 之间。
而任何可打印字符（包括 '0'~'9'）的 ASCII 都远大于 9，因此条件永远为假。
正确的写法应该是：
if (check_range(*password, '0', '9'))   // 检查 ASCII 是否在 48~57 之间
2. 为什么 '\0' 是 0？
'\0' 是空字符（null character），它的 ASCII 码就是 0。
所以 '\0' 与整数 0 在数值上完全相等。
在字符串中，'\0' 用来标记字符串的结尾，比如 while (*password != '\0') 就是在判断是否遇到了字符串结束符。

C 语言中，0 是唯一一个可以被隐式转换为多种类型，且每种转换后都代表某种“零”概念的字面量。
上下文	写法		实际含义
整型		0		整数零
字符		'\0'		ASCII 码为 0 的字符（空字符，字符串结束符）
指针		NULL 或 0	空指针（不指向任何有效地址）
逻辑		0		假（布尔假）

只有字符 '\0' 的 ASCII 码是 0。其他几个“0”并不是 ASCII 码的概念：
    整型 0：是一个整数常量，本身没有 ASCII 码。如果把它赋值给 char 变量，会被解释为 ASCII 码 0 的字符（即 '\0'），但这是一种类型转换，不是它天生就是 ASCII 码。
    指针 NULL 或 0：是空指针常量，通常定义为 0 或 (void*)0。它的整数值是 0，但这个 0 是内存地址的零，不是 ASCII 码。
    逻辑 0：在 C 语言中，0 表示“假”，本质上就是整数 0，同样不是 ASCII 码。
所以，只有 '\0' 这个字符常量的 ASCII 值是 0，其他的“0”是不同上下文中的零值，但它们都可以通过隐式转换与 '\0' 在数值上相等。


在 C 语言里，“声明”这件事是给编译器看的，而“分配内存”是在函数一抬头（刚进入函数时）就全部搞定的。
我们可以用**“酒店订房”**来打个比方：
1. 酒店订房比喻
Python（解释型）：你每走一步，发现需要一张床，才临时去搬一张床进来。没走到那一行，房间里确实没床。
C 语言（编译型）：当你“踏入酒店大门”（调用 check_length 函数）的一瞬间，前台（编译器）就已经查过你的“图纸”了。它知道这个房间里最终需要一张叫 length 的床和一张叫 meets_len_req 的床。
所以，在你还没走到第 26 行时，床位（内存空间）已经给你留好了。
2. 底层真相：栈帧（Stack Frame）的开辟
当你执行到 check_length 的左大括号 { 时，CPU 会执行一段叫 Function Prologue（函数序言） 的汇编代码。
它的核心动作只有一句话：“把栈指针（Stack Pointer）往下挪。”
编译器数了数：你的函数里有一个 int（4 字节）和一个 bool（在栈上通常占 1-4 字节）。
编译器直接命令 CPU：“嘿，给这个函数腾出 8 字节的空间！”
结果：虽然你还没运行到第 26 行，但 meets_len_req 对应的那个内存地址已经属于你了。
3. 为什么能打印出值？
既然空间已经分配了，GDB 作为一个“全知全能”的调试器，它翻了翻你的符号表（Symbol Table）：
GDB 看到：噢，这个函数里有个变量叫 meets_len_req。
GDB 查到：它的地址在栈指针偏移 X 的位置。
GDB 去那个地址看了一眼：发现里面躺着个数字 247。
GDB 就老老实实地告诉你：“报，大王，那块地盘现在确实有个值，是 247。”
这就是为什么即便你还没给它赋值（初始化），你依然能看到一个“垃圾值”。


如果编译器在“函数序言”里把栈指针（Stack Pointer, sp）挪错了，后果通常只有两个字：灾难。
我们可以把栈想象成一个**“垂直摆放的抽屉柜”**，每个函数进来都往下面加几个新抽屉。
1. 如果“挪少了”（空间给不够）
这是最危险的情况，相当于你明明有三个人要住店，却只订了一个单人间。
变量“踩踏”事故：
比如 length 需要 4 字节，meets_len_req 需要 4 字节，但编译器只挪了 4 字节。那么这两个变量就会共享同一个地址。你改了 length，meets_len_req 的值也跟着变了。你的程序逻辑会变得莫名其妙。
摧毁“回家的路”：
在 CS 61C 的汇编部分你会学到，栈上不仅存变量，还存着返回地址（Return Address, ra）。
如果你挪少了，存变量的时候可能会把返回地址给覆盖掉。等函数执行完准备“回家”（回到 main 函数）时，CPU 一看返回地址变成了一堆乱码，程序会直接崩溃（Segfault），或者跳到一个危险的地方。这就是著名的栈溢出攻击（Stack Smashing）。
2. 如果“挪多了”（空间给太多）
这种情况通常不会导致程序立刻崩溃，但它是一种**“公款挥霍”**。
浪费内存：
如果你只需要 8 字节，编译器却挪了 800 字节。虽然程序还能跑，但你白白占用了大量的内存空间。
引发栈溢出（Stack Overflow）：
内存里的栈空间是有限的。如果每个函数都“多拿多占”，特别是当你用递归（函数调自己）的时候，这种浪费会被成千上万倍地放大，很快就会撞到栈的底线，导致程序挂掉。
3. 为什么编译器不会搞错？
既然手动挪 sp 这么危险，为什么我们很少见到编译器出错呢？
静态分析：编译器在翻译你的 C 代码时，会完整地扫描一遍函数。它能精确地数出你定义了多少个变量、每个变量占几个字节、是否需要 Padding 对齐。
固定的公式：在汇编阶段，这个空间大小是一个常量。一旦确定，它在整个函数运行期间都不会变。
小知识：在 61C 的 RISC-V 汇编里，你经常会看到类似 addi sp, sp, -16 的指令。这个 -16 就是编译器计算出来的“完美空间”。

既然所有指针里存的都是地址，那为什么指针还要标类型，如int *a char *a 
1. 解引用（Dereferencing）：到底抓几个字节？
当你写 *p 的时候，你是在命令 CPU 去那个地址拿东西。
    如果 p 是 char *：编译器知道：“哦，去这个地址抓 1 个字节出来。”
    如果 p 是 int *：编译器知道：“去这个地址抓 4 个字节出来。”
    如果 p 是 double *：编译器知道：“去这个地址抓 8 个字节出来。”
如果没有类型，CPU 站在内存地址面前会一脸懵逼：我到底该往后读多少位才算完？
2. 指针运算（Pointer Arithmetic）：跨度是多少？
这是你目前在做实验（比如遍历字符串或数组）时最常用的功能。当你写 p + 1 时，它并不是简单的“地址 + 1”。
指针类型		执行 p + 1 后，地址实际增加的值		理由
char *p		+ 1							char 占 1 字节，跳到下一个字符。
int *p		+ 4							int 占 4 字节，跳过一整个整数。
double *p		+ 8							double 占 8 字节，跳过一整个浮点数。
如果没有类型，编译器就不知道 p + 1 到底是想让你移到隔壁，还是移到三个街区外。
3. 数据解释（Interpretation）：这串 01 是什么意思？
内存里存的全是 0 和 1。同样的 4 个字节：
    如果它是 int，它代表一个整数。
    如果它是 float，它代表一个小数。
编译器需要通过指针的类型，来决定用什么样的指令去处理抓回来的数据。你总不想让 CPU 用处理整数的逻辑去算你的工资（小数）吧？
