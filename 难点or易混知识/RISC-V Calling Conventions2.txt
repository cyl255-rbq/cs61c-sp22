1. CC 的适用范围与目的 (b, c)
适用场景： CC 主要约束的是函数间的跳转（Function Calls）。如果你只是在函数内部写个循环（Loop）或分支（Branch），那是你“自家领地”，你可以随心所欲地用寄存器。
目的： 为了抽象。你写函数时不需要知道调用你的人是谁，也不需要知道你调用的函数内部是怎么实现的。只要大家都遵守 CC，代码就能无缝拼接。
2. 寄存器的“生而平等”与“职能划分” (f, t, v)
物理上： 除了 x0（恒为 0）和初始化的 sp，其余 32 个寄存器在硬件层面上几乎是一模一样的。
逻辑上： CC 给它们发了“工牌”。
s 开头的是“行政资产”，用完得还。
t 开头的是“一次性草稿纸”，随便改。
手段不限 (t)： 只要你能保证该还原的寄存器在函数返回时原封不动，你是通过堆栈（Stack）保存的，还是压根没动它，甚至是通过加减抵消算的，都没人管你。
3. 栈（Stack）的管理艺术 (h, i, m, r)
栈是函数存放临时数据的“私人领地”。
分配空间 (i)： addi sp, sp, -offset。在 RISC-V 中，栈是向低地址增长的。向下移动 sp 就像是在地上挖个坑，坑里的空间就是你的了。
边界定义 (h)： 规则规定：sp 以上的数据是别人的（不能碰），sp 以下的是荒地（你可以开垦）。
恢复原状 (m, r)： 当函数结束时，你必须把 sp 移回原来的位置。如果你“挖了坑不填”，调用者回来时 sp 乱了，它就找不到自己的数据了。
4. 谁该负责保存？（核心考点：l, o, p, s）
这是最容易混淆的地方，可以记成两类：
Callee-saved (被调用者负责还原): s 寄存器, sp
如果函数 B（Callee）想用 s0，它必须：
先把 A（Caller）存在 s0 里的旧值存到栈里。
用 s0 办自己的事。
返回前，从栈里把旧值取出来还给 s0。
结论： 对于 Caller 来说，它觉得 s 寄存器是“安全的”（Persistent）。
Caller-saved (调用者负责保存): t 寄存器, a 寄存器, ra
如果函数 A（Caller）在 t0 里存了重要数据，接着调用了 B：
A 必须默认 B 会把 t0 弄乱。
A 如果还想要那个数，得在跳到 B 之前自己把它存到栈里。
结论： 对于 Callee 来说，它可以自由蹂躏 t 和 a 寄存器，不需要还原。
注意 ra (p)： ra 存放的是返回地址。一旦 B 里面还要调用 C，ra 就会被覆盖。所以 B 必须在开头把 ra 存起来，否则它就“找不到回 A 的家门”了。
补充：关于效率
标准答案里提到 “寄存器访问比内存（栈）快几个数量级”。
优化策略： 尽量多用寄存器。如果你写一个不调用其他函数的叶子函数（Leaf Function），尽量全用 t 寄存器，这样连栈都不用开，速度飞快。

“既然不保存会丢地址，为什么不规定调用者可以假设 ra 不变呢？”
原因在于 jal 指令的硬件逻辑。
当你执行 jal ra, Function_B 时，硬件会自动把下一条指令的地址（返回地址）塞进 ra。这个动作是强制性且不可逆的。
想象一下这个场景（函数 A 调用 B，B 再调用 C）：
Main 调用 A： 此时 ra 指向 Main。
A 调用 B： 执行 jal ra, B。此时 ra 里的“Main 地址”瞬间被覆盖成了“A 的下一行”。
重点来了： 如果我们规定“调用者 A 可以假设 ra 不变”，那么 B 就必须在返回 A 之前，把 ra 还原成“指向 Main 的地址”。
为什么不这么规定？
开销太重： 如果 ra 是 Callee-saved（被调用者负责还原），那么每一个函数（只要它不是叶子函数）都必须在开头压栈 ra，结尾弹栈 ra。
逻辑矛盾： ra 本身就是为了告诉 B “该回哪去”。如果 B 把 ra 还原成了 Main 的地址，那 B 执行 ret (也就是 jalr x0, 0(ra)) 时，它就直接跳回 Main 了，根本回不去 A！
正确的逻辑是：
ra 是 Caller-saved（或者叫 volatile）。这意味着，如果函数 A 还要用它的 ra（因为它还要回 Main），A 必须在调用 B 之前，自己把 ra 存到栈里。B 返回后，A 再从栈里把“回家的路”取出来。


为什么栈是从高地址往低增长？（那个奇怪的 Bottom）
这个命名确实非常反直觉。我们要分清**“物理位置”和“逻辑名称”**。
为什么叫 Bottom？
在 RISC-V 的内存布局（Memory Map）中，地址空间像一栋楼：
楼顶（高地址）： 给栈（Stack）用。
地基（低地址）： 给代码（Code/Text）和静态数据用。
在你的 HW4.4 文本里，它把 sp 称为 Bottom，是因为它把栈看作一个**“深渊”**。
栈的起点（高地址）是地表。
随着你存的东西越来越多，你挖的坑就越来越深（地址越来越小）。
sp 永远指向这个坑的最深处。 在某些定义里，深渊的最深处就被称为“底”（Bottom）。
为什么非要往低地址增长？
这其实是一个极其聪明的节省空间的设计：
堆（Heap） 是往高地址长的（向上长）。
栈（Stack） 是往低地址长的（向下长）。
它们两个相对而行，中间剩下的空白区域是共用的。如果栈也向上长，那你就得预先规定栈占哪块、堆占哪块，万一栈满了但堆还空着，空间就浪费了。现在这种“双向奔赴”的设计，只要中间还有空位，谁都能用。
3. 4(sp) 既然是往高了存，为什么说栈是向下长的？
这正是最容易把人绕晕的地方。我们要区分 “开辟空间” 和 “读写数据”：
开辟空间（向下挖坑）： 你要存两个字（8 bytes），你必须先执行 addi sp, sp, -8。这时候 sp 往低地址跳了 8 位，相当于你在深渊里多挖了 8 层的深度。
存取数据（在坑里放东西）： 现在你站在坑底（新的 sp 位置）。你想把第一个数放在你刚挖出来的这 8 个字节的空间里：
第一个字放在 0(sp)（就在脚下）。
第二个字放在 4(sp)（在你头顶上方 4 字节处）。
所以： * 说它“向下增长”，是指 sp 寄存器数值的变动方向。
使用 4(sp) 这种正偏移，是因为 sp 已经提前降到了最低点，我们要往回（向高地址方向）去填满刚才预留出来的那段空间。
总结
递归： 为了不让不同层级的“自己”互相打架（覆盖 ra 和变量）。
Bottom： 题里的定义，指代的是深渊的最深处（数值最小的地址）。
正偏移（4(sp)）： 因为你已经把 sp 降到了地窖地板，存东西当然是往天花板方向（高地址）存。
关于 4(sp) 和 addi sp, sp, -8 的先后顺序，你在写 C 语言转汇编的时候，有没有试过如果不先减 sp 直接存数据会发生什么后果？


CC 的本质是“外交政策”： 它是为了处理你和别人的函数之间的关系。比如你调用了 printf，你需要知道哪些寄存器会被它弄乱。
Loop 是“内政”： j loop 只是在同一个函数内部跳来跳去。这个函数里的所有寄存器都在你的掌控之下。你清楚地知道 t0 现在存的是计数器，不需要为了跳个循环就死板地遵循“必须把某某寄存器存到栈里”这种 CC 规则。
总结： 在同一个函数内部，你怎么折腾寄存器都行，只要你在**出这个函数（返回给调用者）**之前，按 CC 规则把该还的还了就行。

1. 递归为什么必须“新开一个空间”？
你觉得递归和循环很像，直觉上是对的，因为它们都在重复逻辑。但递归本质上是函数调用（Function Call），这导致了两个无法回避的问题：
RA（返回地址）的覆盖：
循环（Loop）不需要回跳到“调用它的那一页”，它只是在原地打转。但递归函数 f(n) 调用 f(n-1) 时，必须用 jal ra 跳过去。这一跳，ra 就会被覆盖。如果不新开一个栈空间把当前的 ra 存起来，等你递归到最深层想要往回返的时候，你会发现 ra 里全是最后一层的地址，你永远回不去了。
局部变量的“分身”问题：
在循环里，你通常只有一个计数器 i。但在递归里，每一层递归都有自己的参数 n。如果你不给每一层开辟独立的内存空间，那么 f(5) 的 n 和 f(4) 的 n 就会挤在同一个寄存器里。当你从 f(4) 返回到 f(5) 时，你会发现 f(5) 原本的 n 已经被改成了 4。
一句话总结： 递归需要保存“案发现场”，为了让每一层函数返回时，它的局部变量和返回路径都能原封不动地恢复。

1. 关于 (a)：Loop 到底是不是“新函数”？
结论：完全不是。
你的直觉认为“跳过去就是一个新开始”，但在底层架构层面，Loop 和 Function 有两个本质区别：
没有 ra 的参与： 当你执行 jal ra, Function 时，硬件会自动把返回地址存入 ra。但当你执行 j Loop（伪指令，实际是 jal x0, Loop）时，ra 是不会变的。这意味着程序并不打算“跳回来”，它只是在原地打转。
没有“上下文切换”的需求： * 函数调用是为了去执行一段你可能完全不了解的代码（比如调用库函数），所以必须用 CC 规则来保证双方不互相干扰。
Loop 是你自己写的代码逻辑的一部分。你在 Loop 之前定义的 t0，在 Loop 里面当然可以直接用。如果你把 Loop 当成函数，那意味着每次循环你都要：压栈保存寄存器 → 执行循环体 → 出栈恢复寄存器。这会让程序的性能下降几十倍。
一句话总结： 函数是“外交”，必须讲礼仪（遵循 CC）；循环是“内政”，怎么省事怎么来。
