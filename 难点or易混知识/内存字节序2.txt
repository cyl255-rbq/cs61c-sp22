字节序它到底是一个“存钱的规则”，还是一个“取钱的规则”？
答案是：它是 CPU 的“整套动作规范”。 存的时候按这个规矩拆，读的时候按这个规矩拼。
你之所以觉得 Q1 和 Q2 的逻辑“打架”了，是因为这两道题的出发点完全不同。我们把它们放在天平两端对比一下：
情况 A：Q1 —— “现成的字节，不同的解释”
出发点： 内存里已经躺着 4 个字节了：00 01 FF FF。题目没说它们是怎么来的（可能是从大端序网络传来的，也可能是外星人写的）。
题目的灵魂拷问： “如果现在派一个大端序 CPU 和一个小端序 CPU 过来读这块内存，它们分别会看到什么？”
大端序 CPU 读： 它认为“前面的就是大头”。
拼法：00是高位，FF是低位 → 0x0001FFFF。
小端序 CPU 读： 它认为“前面的就是小头”。
拼法：把这 4 个数倒过来拼 → 0xFFFF0100。
结论： 这种情况是在考你**“不同协议的解读方式”**。这就像同一个单词 "Gift"，在英语里是“礼物”，在德语里是“毒药”。东西没变，解读的脑子变了。
情况 B：Q2 —— “同一种脑子，自圆其说”
出发点： 题目明确说了“假设我们有一个小端序系统”。
题目的执行过程：
存（Store）： 执行 x[0] = 0xDEADBEEF。因为 CPU 是小端序，它会把这个数倒着塞进内存，变成 EF BE AD DE。
读（Load）： 执行 y = *(uint64_t*)x。这个 CPU 依然是那个小端序 CPU，它去读内存时，知道自己之前是倒着存的，所以它会再倒一次拼回来。
既然“存”和“读”都用同一套规则，为什么 Q2.3 的结果 y 会变样呢？
不是因为 Endianness 变了。
是因为读取的长度（Size）变了！你存的时候是两个 4 字节的小块，读的时候非要把它当成一个 8 字节的大块。
你的核心疑问：CPU 存的是不是一样？
“还是说是 CPU 无论小端序还是大端序都存的一样，然后读的时候区分？”
绝对不是！ * 大端序 CPU 存 0x12345678，内存里是：12 34 56 78。
小端序 CPU 存 0x12345678，内存里是：78 56 34 12。
它们在内存里的物理排列是完全不同的。
那为什么 Q1 看起来像是“存的一样，读的区分”？
那是因为 Q1 模拟的是**“跨平台交流”**的尴尬场景。
比如：
一个大端序服务器（网络标准通常是大端）发来了一个 0x0001FFFF。
它把字节 00 01 FF FF 扔进了你的内存。
你的 小端序 CPU 傻呵呵地去读，结果读成了 0xFFFF0100（-65280）。
这就是为什么 Q1 要分两种情况考你。它不是说存的一样，它是考你：如果内存已经固定长这样了，不同规则的 CPU 会产生多大的误会。
总结
Endianness 决定了“存”和“读”的镜像对应关系。 只要你用同一种 CPU 存、同一种 CPU 读，且读写的长度一致，你就永远感觉不到 Endianness 的存在。
只有在以下两种情况你会“感觉到”它：
跨设备：大端序存，小端序读（Q1 的考点）。
跨长度：用 int 存，用 char 或 long 读（Q2 的考点）。
