关键原因
在OpenMP规范中，#pragma omp paraLlel for 有一条至高无上的特例条款：
规定：紧跟在 #pragma omp parallel for 后面的那个循环控制变量（也就是这里的i），无论
你在外面把它定义成什么（即使定义成了全局变量或普通的局部变量），OpenMP在编译时都一定
会强行把它变成每个线程私有的(Private)。

注意看这两个循环变量i和j的待遇差别：
对于外层循环变量i：
因为它是紧跟在 #pragmaomp parallelfor 后面的直接控制变量。根据我们上面说的特例
条款，i被成功且自动地私有化了。每个线程分到的i范围不同，这没问题。
2对于内层循环变量j：
重点来了！OpenMP的自动私有化特权，只对紧跟在它后面的那“一层"循环变量有效。对于内

在并行区域（#pragma）外面声明的，所以j是所有线程共享的(Shared)!

只有紧跟的第一个无论是在内在外声明会被自动私有化

// 将数组arr 的第i 个元素减 1。n 是 omp-get_num_threads（）的整数倍
#pragma omp parallel
{
	int threadCount = omp-get_num_threads();
	int myThread = omp-get_thread_num();
	for （int i=θ;i<n;i++）{
		if (i % threadCount == myThread) arr[i] -= 1;
}
【翻译】
问题：会引发伪共享（False Sharing)问题。
理由：伪共享之所以会发生，是因为不同的线程在同一时间修改了位于同一个内存硬件区块（即缓
存行CacheLine）中的不同元素。这在硬件层面是一个严重的问题：当某个线程修改了arr[i]
时，它会强行让自己及其他线程中包含该元素的整个CPU缓存行直接失效（Invalidating)。如果其他
线程接下来要修改相邻的元素，就必须重新去主内存中拉取最新的缓存，从而导致极其严重的性能
恶化。
【深度解析】
代码意图：这段代码通过交错取模的方式（i %threadCount== myThread）手动给各个线
程分配任务。例如有2个线程：
o线程0负责：arr[θ]，arr[2]，arr[4]，arr[6] ….
o线程1负责：arr[1]，arr[3]，arr[5]，arr[7] ….
为什么是灾难性的“伪共享”：
在计算机硬件中，CPU并不是按单个字节或单个int读写内存的，而是以缓存行（Cache
Line，通常是64字节)为单位。
arr[θ]和arr[1]物理上紧挨在一起，绝对在同一个缓存行里。当线程O试图修改
arr[θ］，线程1试图修改arr[1]时，它们为了争夺这同一个缓存行的写权限，会在CPU核
之间来回搬运、频繁锁死和刷新缓存。这种现象在业务逻辑上是正确的（各算各的），但在硬
件底层却在“打架”，会导致多线程的速度比单线程慢上百倍。标准的做法是使用omp
parallelfor让线程处理连续的、大块的数据块。
