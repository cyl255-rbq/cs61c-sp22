假设数组总长度 NUM_ELEMS=6。
SIMD循环处理了前4个元素（i=θ，1，2，3）。
剩下的尾部元素有2个：i=4 和i=5。
假设这两个尾部元素的值分别是：
ovals[4]=1θ(小于128，不该加)
vals[5] = 200(大于128，应该加)
我们来看看这两种代码分别是怎么执行的：
写法一（正确）：放进里面的if语句
for (unsigned int i = 4;i< 6;i++){
if (vals[i] >= 128)  result += vals[i]; }
}
i=4 时：i<6 成立，进入循环。检查if（1θ >=128）为假，什么都不做。循环继
续。
i=5时：i<6成立，进入循环。检查if（200 >=128）为真，result += 200。
最终结果：成功把200加进去了。
写法二（错误）：放进for的终止条件里
for （unsigned int i = 4;i< 6 && vals[i] >= 128;i++）{
result += vals[i];
}
i=4时：CPU检查for 循环的继续条件：i<6&&vals[4]>=128。
oi<6是真。
ovals[4] >= 128（即10>=128）是假。
o真&&假→结果为假。
发生惨剧：因为整个循环条件不满足，for 循环立刻在i=4 的时候当场终止
（Terminate）！*最终结果：CPU直接跳出了循环，i=5的那个20θ连被看一眼的机会
都没有，直接被漏掉了。
结论
在C语言中，for（初始化；条件；增量）的规则是：只要“条件"变为假，循环就地彻底结束。
你的第二种写法，要求尾部剩下的元素必须连续、每一个都必须≥128。只要中间混进进-
小于128的倒霉蛋，后面的数据就全断流了。



为什么把 int tmp_arr[4];改成long long int tmp_arr[4];也报错?
你的直觉其实非常敏锐！你想着：“既然最终结果result 会溢出，那我干脆把用来接应数据的临时
数组tmp_arr 也升级成64位的LongLong int，这样不就绝对安全了吗？”
这个想法从防溢出的角度来看很合理，但你忽略了一个残酷的底层物理现实：当你改变了数组的数
据类型，整个内存的“格子大小"就全变了，导致硬件在存数据时发生了严重的“萝卜投错坑"惨剧。
无论是编译直接报错，还是运行后测试失败（TestFailed），原因都出在位宽不匹配上。
1.算一算总账：位宽彻底对不上了
_mm_storeu_si128这个函数名字里的128是个死脑筋。不管你用大括号怎么强制类型转换，它
在底层硬件上永远只会从寄存器里倒出128位（16字节）的数据。
当你用int tmp_arr[4]时:
每个int占32位，32×4=128位。寄存器里的数据倒出来，刚好完美地一人分一个格
子。
当你改成 Long Long int tmp_arr[4]时:
每个Long Long 占64位，4个格子总共需要64× 4= 256位!
2.错位惨剧：数据被“揉成了一团’
当 128 位的数据强行写入一个 256位宽的LongLong 数组时，内存里发生了极其诡异的排列:
假设你的 SIMD 寄存器 sum_vec 里算出来的4个32位整数分别是：［D，C，B，A ］。
由于_mm_storeu_si128 只管按顺序扔出 128位，而Long Long 的格子比以前大了一倍：
1.tmp_arr[θ］（64位大格子）：把32位的A和32位的B强行揉成了—个数（B变成了高32位，
A变成了低32位）。
2.tmp_arr[1]（64位大格子）：把32位的c和32位的D揉成了第二个数。
3.tmp_arr[2]和tmp_arr[3]：因为128位的数据已经全被前两个格子吸干了，这两个格子什
么都没分到，里面全是一开始的随机内存垃圾值！


当你写下_mm_storeu_si128（（__m128i *）tmp_arr，sum_vec）；时，底层发生的事情就像流水
线卸货一样简单粗暴：
ACPU收到指令：把sum_vec寄存器里的16个字节（128位），一股脑喷到tmp_arr的起始
内存地址上。
内存是一条连续的传送带，16个字节的数据就像一摊水一样铺了过去。
1.当接应数组是inttmp_arr［4］时（每格4字节）：
这16个字节平铺过去，刚好精准地填满了4个格子。
0第0~3字节→进了tmp_arr[θ]
第4~7字节→进了tmp_arr[1]
第8~11字节→进了tmp_arr[2]
第12~15字节→进了7tmp_arr[3]
各回各家，皆大欢喜。
2.当接应数组是LongLongtmp_arr[4]时（每格8字节）：
内存传送带上的格子变大了一倍，但喷出来的水（128位数据）总量还是那么多。
结果就是你说的“融合”：
o前8个字节（原本是第1和第2个int）全部陷进了第一个大格子tmp_arr[θ］里。
o后8个字节（原本是第3和第4个int）全部陷进了第二个大格子tmp_arr[1]里。
o至于后面的tmp_arr[2]和tmp_arr[3]，因为那16字节的数据到这里已经"喷完了”，它们
根本没被充值，里面依然是内存里原本就有的随机垃圾值。
