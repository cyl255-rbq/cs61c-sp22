栈内存：在栈上定义的独立变量（比如函数里的 int a; char b;），编译器通常会表现得非常“奢侈”：
    懒政原则：为了让 CPU 访问速度最快，编译器往往给每个独立的变量都分配一个完整的 Word（4 字节或 8 字节）。
    安全距离：在独立变量之间留出足够的空间，可以防止某些细微的内存溢出（Buffer Overflow）互相干扰。
    管理简单：每个变量都对齐到 Word 边界，编译器计算地址时非常简单，不需要考虑“半个字节”的问题。
在 64 位系统里，CPU 的“手”确实是 8 个字节。所以，我们可以把一个 Word（8 字节）看作“一整行”。
假设有个变量占了 0-5 号位，你的 int（4字节）非要从 6 号位开始停：
    它会占用：6, 7（第一行的尾巴）和 8, 9（第二行的头）。
    这时候 CPU 就疯了：它得抓第一行拿 6-7，再抓第二行拿 8-9，然后拼起来。
所以，对齐的本质就是： 别让变量横跨在 CPU 的“抓取边界”上。

在结构体里，比如是按照自身倍数原则且整体是类型最大字节的倍数
比如double int char和int double char和int char double分别是8+4+1+3和4+4+8+1+7和4+1+3+8
为什么不能 4+1+8？因为程序员可能会通过指针偏移来访问成员。如果编译器偷偷换了位置，你的指针代码就会直接指向错误的数据，程序就崩了。
整体是类型最大字节的倍数因为假如有个结构体数组如student a[2]，如果是按int double char的话 
int a：地址 0（对齐 4，没问题）
double b：地址 8（对齐 8，没问题）
char c：地址 16（对齐 1，没问题）
结束地址：16。
第二个结构体（紧接着从地址 17 开始）：
    int a：地址 17。坏了！ int 要求地址是 4 的倍数，17 明显不是。
    double b：地址 25（17 加上偏移量 8）。又坏了！ double 要求地址是 8 的倍数，25 明显不是。
这就是为什么要凑够 24 字节：
为了保证在数组里，每一个结构体里的每一个成员，都能精准地落在它要求的倍数地址上。24 是 8 的倍数
所以第二个结构体会从 24 开始，它的每一个成员就又能完美对齐了。

你可能会想：既然编译器会乱塞 Padding，那我怎么知道 b 到底被挤到哪去了？
1. 以前的“硬核”做法：肉眼计算
在早期的嵌入式开发中，程序员确实会拿着手册（ABI 规范）去人工计算：
    “我知道 int 占 4，后面接 double 肯定要补 4 个 Padding，所以 double 肯定在偏移量 8 的位置。”
2. 现在的“黑科技”：offsetof 宏
C 语言标准库提供了一个叫 offsetof 的宏（在 <stddef.h> 中）。你不需要自己算，编译器会告诉你：
C
#include <stddef.h>
size_t offset = offsetof(struct MyStruct, b); // 编译器直接告诉你偏移量是 8
因为编译器亲手塞的 Padding，它心里最清楚 b 在哪。
3. 为什么编译器不能“偷偷改顺序”？
你说：“既然编译器知道 Padding，那它顺便帮我把顺序改了（比如把 char 塞进 int 后面的空隙）不就更完美了吗？”
答案是：为了“契约精神”。
很多时候，C 语言写的程序要和外界打交道：
    网络传输：你把一个 struct 直接通过网线发给另一台电脑。如果你的编译器偷偷改了顺序，而另一台电脑的编译器没改，那对方接到的数据就是一团乱码。
    文件存储：你把结构体存进硬盘，十年后读取。如果这期间编译器更新了，“自作聪明”地换了顺序，你的旧数据就全毁了。
    硬件驱动：很多硬件寄存器的位置是固定的（比如前 4 字节是控制开关，后 8 字节是数据）。如果编译器乱改顺序，你原本想开灯，结果可能直接把机器给烧了。


角色分配
    程序员（你）：甲方。你下令：“我要一个结构体，里面住一个 int 和一个 char。”
    编译器（GCC）：建筑设计师。它负责画图纸，决定每个房间（变量）在内存里的精确经纬度（地址）。
    CPU：搬运工。它只管按照图纸上的地址去搬东西。
为什么编译器对“结构体”和“栈”区别对待？
虽然 CPU 都不认识它们，但编译器在画图纸时，脑子里的想法是不一样的：
在结构体里（行李箱模式）：
编译器想：“这个结构体可能会被打包发到网上，或者存进硬盘。为了省流量、省空间，我得让成员们尽量住得近一点。”
所以，它会让 int 和 char 挤在同一个 8 字节的格子里。
在栈里（单间公寓模式）：
编译器想：“这里的变量都是临时的，只有我（编译器）自己知道它们在哪。为了我计算地址方便，也为了 CPU 抓取最快，我干脆给每个人发一整行（8 字节）的地址，省得我去算‘谁和谁挤在一起’这种麻烦账。”


1. 为什么不让编译器去处理 int 跨字节（如 3, 4, 5, 6）？
其实，编译器可以处理，但它不想处理。这就像你可以用筷子喝汤，但大家都建议你用勺子——因为效率差太多了。
理由 A：性能税（Performance Tax）
如果一个 int 跨了边界，编译器为了让你拿到这个数，必须生成好几倍的汇编代码：
发出第一条指令：去抓包含 3 的那一块（地址 0-7）。
发出第二条指令：去抓包含 8 的那一块（地址 8-15）。
发出第三、四条指令：把抓回来的碎片进行**左移、右移、按位或（OR）**拼接起来。
原本 CPU 一个动作就能干完的事，现在要跑 4-5 个动作。在 CS 61C 的世界里，性能就是生命。编译器默认选择“牺牲一点点内存空间（Padding）”来换取“极致的运行速度”。
理由 B：硬件的“物理阉割”
你正在学的 RISC-V 或者是 MIPS 这种精简指令集 CPU，在硬件电路设计上就非常“硬核”：
它的 lw (Load Word) 指令内部电路直接规定了地址必须是 4 的倍数。如果你传个地址 3 进去，硬件电路会直接触发一个信号（Exception），告诉操作系统：“这活儿我干不了，这人写代码不规矩。” 然后系统就直接把你的程序 Segmentation Fault 了。
2. 结构体怎么“发到网上”？它不是只存在于运行中吗？
这是个很棒的误区。我们要区分两个概念：“图纸”和“实体”。
结构体定义（你在 .h 或 .c 里写的代码）：那是建筑图纸。它确实只存在于你的代码和编译器的脑子里。
结构体变量（你 malloc 出来的或者定义的 s1）：那是真实的房子。它在内存里占据着实实在在的字节（0 和 1）。
怎么发给别人？
虽然“图纸”发不过去，但你可以把**“房子里的砖头”**按顺序拆下来扔过去。
当你调用 send(socket, &s1, sizeof(s1), 0); 时，操作系统干了这么件事：
它从 &s1 这个地址开始。
连续数出 sizeof(s1) 个字节（假设是 16 字节）。
把这 16 字节的“二进制原始数据”像流水一样通过网线发给另一台电脑。
