你之所以不能直接写 addi x1, x0, label，最根本的原因只有四个字：装不下去。
1. 为什么 label 不能直接代替实际地址？
你要记住，label 在编译器眼里最终就是一个 32 位的数字（地址）。
物理限制：
我们来看一条 addi 指令的内部结构：
一条 RISC-V 指令总共只有 32 bits。
addi 是 I-type 指令，它留给“立即数（immediate）”的位置只有 12 bits。
12 bits 最大只能表示到 2047。
如果你要找的 label 地址是 0x80004ABC：
这个数字太大了，根本塞不进 addi 那小小的 12 位格子里。如果你强行写 addi x1, x0, 0x80004ABC，编译器会直接报错：“Immediate fragment too large”。
2. 具体的例子：它是怎么“跳”的？
假设你的程序长这样，你想把 target 标签的地址加载到 x10：
Code snippet
0x1000: auipc x10, 0x70004    # la 伪指令的第一步
0x1004: addi  x10, x10, 0xABC  # la 伪指令的第二步
...
0x71004BC: target: .word 42    # 这是我们要找的目标
第一步：auipc（算出大致范围）
编译器计算出 target 距离当前位置（PC=0x1000）大约有 0x71003BC 那么远。
它先执行 auipc x10, 0x71004：
它把 0x71004 左移 12 位 → 0x71004000。
加上当前 PC（0x1000）→ x10 = 0x71005000。
这时，x10 已经指向了目标附近的“大门口”。
第二步：addi（精确定位）
通过刚才的加法，我们可能稍微走过头了一点点，或者还没到。
执行 addi x10, x10, -0x444（举例数值）：
在 x10 的基础上加上偏移量，最后精准地让 x10 = 0x71004BC。
这就是 la 存在的意义： 你写一行 la x10, target，汇编器帮你自动计算这两步复杂的数学题，帮你避开了 12 位立即数的限制。
3. 为什么一定要用这种“相对”的方法？（PC-relative）
你可能会问：“既然地址是确定的，为什么不直接用 lui 这种绝对定位，非要用 auipc 加上当前的 PC 这么麻烦？”
这就是为了“代码搬家”：
想象一下，你写好了一个牛逼的函数，地址是 0x100。
绝对寻址（LUI）： 代码里写死了“去地址 0x100 找我”。如果别人把你的函数放到了内存的 0x500 位置，程序就直接找错人了。
相对寻址（AUIPC）： 代码里写的是“从我站的地方往后走 10 步找我”。无论你的函数被整体搬迁到内存的哪个角落，“10 步”这个相对距离是不变的。
这种特性叫 Position Independent Code (PIC)。现代操作系统为了安全，每次运行程序时加载的内存地址可能都不一样，只有用 auipc 这种相对寻址，程序才能正常运行。
4. 总结
label 本质是地址，但地址太长（32 位），addi（12 位立即数）塞不下。
la 是“装修工”，它把一个大动作拆成两步：先用 auipc 走大步，再用 addi 挪小步。
不直接写死地址，是为了让你的程序在内存任何地方都能跑。

1. 怎么知道 target 这个 label 对应的地址？
结论：CPU 不知道，但“翻译官”（汇编器和链接器）知道。
当你写汇编代码时，target 只是一个人类可读的符号。整个“翻译”过程分两步：
汇编阶段 (Assembler)： 汇编器会扫描两遍你的代码。第一遍它会建立一张符号表 (Symbol Table)，记录下每个 label 出现在哪一行。比如它看到 target 在第 100 行指令处，而每条指令 4 字节，它就知道 target 相对于程序开头的偏移量是 400 字节。
链接阶段 (Linker)： 当你把多个文件拼成一个程序时，链接器会决定整个程序在内存中的具体“户口本地址”（比如从 0x10000 开始）。这时候，链接器会根据偏移量算出 target 的确切物理地址。
最后： 链接器会把代码里的 la x10, target 替换成具体的、算好的 auipc 和 addi 指令。当 CPU 拿到指令时，里面已经不是 target 这个字母了，而是算好的数字。
2. 怎么“拆分” 32 位地址？（指令不是已经占满了吗？）
你问到了一个关键点：拆分这个动作，不是在程序运行的时候做的，而是在“翻译”的时候做的。
谁来拆？ 汇编器 (Assembler)。
怎么拆？ 假设你要加载 0x12345678。
汇编器发现这数太大（32位），塞不进一条指令。
它把这个数切开：高 20 位是 0x12345，低 12 位是 0x678。
它生成两条 32 位的指令：
lui x10, 0x12345 （这 32 位指令里存了 0x12345 这个数字）
addi x10, x10, 0x678 （这 32 位指令里存了 0x678 这个数字）
占满了怎么办？ 没错，指令确实只有 32 位。所以我们需要两条指令（共 64 位）来协作完成“搬运一个 32 位数字”的任务。CPU 运行代码时，只是机械地执行这两条指令，执行完后，寄存器里就拼出了那个 32 位的完整数字。
3. auipc 为什么要加 PC？（尤其是大 PC 加小 Target 的情况）
你的疑问很有道理：为什么要加 PC 这种“变量”，而不是直接算差值？
为什么加 PC 的目的是什么？
目的就是“ Position Independent (位置无关)”。
如果你的代码写死 Target = 0x00000001，那你的程序只能放在内存地址 0 的位置跑。一旦操作系统把你挪到 0x78889999，程序就崩了。
但如果代码写的是 Target = PC + 偏移量，那么无论程序搬到哪，PC 和 Target 之间的“相对距离”是不变的。只要偏移量是对的，程序永远能找到目标。
面对“大 PC 加小 Target”怎么办？（比如 PC = 0x78889999, Target = 0x00000001）
你担心要“减去巨量的东西”，其实在计算机里，减法就是加负数。
算差值： 汇编器会算：Offset=Target−PC=0x00000001−0x78889999。
补码表示： 这个差值是一个巨大的负数（在 32 位系统里是 0x87776668）。
拆分执行：
auipc 加上这个负数的高位。
addi 加上这个负数的低位。
在二进制层面，加法器不分正负。把这个巨大的“补码”加到 0x78889999 上，结果会发生溢出，而溢出后的结果正好就是 0x00000001！

编译器的打包机制。
你能保证“相对距离不变”，是因为指令和变量被紧紧地打包在了同一个**二进制镜像（Binary Image）**里。
你可以把这个过程想象成**“盖楼”**：
1. 编译器的“设计图”：分段（Sections）
当你写汇编代码时，你会看到类似这样的声明：
.text：这是放指令的地方。
.data：这是放初始化好的变量（比如全局数组）的地方。
编译器（Assembler）在干活时，会像建筑师一样，把 .text 里的指令排成一队，紧接着把 .data 里的变量排成另一队，然后把它们缝合在一起，形成一个完整的文件。
2. 链接器（Linker）的“焊死”操作
当你把程序编译成可执行文件时，链接器会决定：
指令排在文件的偏移量 0 到 0x500。
变量排在文件的偏移量 0x500 到 0x800。
在这个可执行文件里，指令和变量的相对位置已经“焊死”了。
指令 A 在文件的第 100 字节。
变量 B 在文件的第 600 字节。
它们的相对距离永远是 600−100=500 字节。
3. 加载器的“整体搬迁”
当你运行程序时，操作系统（Loader）会把这个二进制文件完整地读入内存。
就像我们之前说的“火车”比喻：
不管操作系统把这列火车停在 1 号站台（地址 0x1000）还是 5 号站台（地址 0x5000）。
只要火车本身没断开，车头（指令）和车尾（变量）的距离就永远是 500 字节。
这就保证了无论 auipc 取到的 PC 值是多少，加上那个固定的“偏移量”，最后落下的点永远是那个变量。
4. 什么时候相对距离会变？
并不是所有的变量都能保证相对距离不变。以下情况“距离”会失效：
堆空间（Heap）： 当你用 malloc 申请内存时，内存是在程序运行过程中从操作系统那里“临时要”的。这块地皮在哪完全看运气，所以它和指令之间的距离是随机的。
动态链接库（DLL / .so）： 如果你的变量在另一个文件里（比如系统库里的变量），那么你的程序和那个库被加载的位置可能天差地远，距离就不固定了。
