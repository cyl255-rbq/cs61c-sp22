int j；// 注意：j声明在并行区域外面！
#pragma omp parallel for

	for（j=θ；j<1024;j++）// 灾难现场
		A[i + j*1024] = i + j*1024;

原理解析：
OpenMP的 #pragma omp parallelfor 只会自动把紧随其后的那个循环变量（这里是i）
变成线程私有（private）。
而内层的循环变量」是在外面声明的，它默认是shared（共享）的！
翻车过程：
假设线程A负责 i=θ，线程B负责i=1。它们同时启动。
线程A刚进入内层循环，把j设为0。
还没等线程A跑完，线程B突然插一脚，把公共的j改成了5。
此时线程A算索引i+j*1024 时，用的j突然变成了5！这就导致：有的内存位置被重复
写入，而有的位置（比如j=1，2，3）直接被漏掉了。
结论：内部循环变量一旦共享，多线程之间会互相践踏j的值，导致最终数组里的数据混乱
不堪，得到(a) Incorrect result。

1.它的目的是什么？
它的目的很简单：把数组A里的每一个数字，全部变成它的相反数（正数变负数，负数变正数）。
比如数组原本是[1，2，3，4］，执行完后变成［-1，-2，-3，-4］。
2.正常单线程（串行）会怎么写？
如果让你写一个普通的单线程程序来做这件事，你肯定会这么写：

//正常的单线程串行写法
for （int i = 0;i< 1048576;i++）{
A[i]=-A[i]；//老老实实从第θ个改到最后一个
这个代码非常直观，CPU从i=θ一直数到1048576，每数到一个，就把对应的A[i]取反。

那作者为什么要写这么复杂的if（i%线程数==线程号）呢？
他是想玩一种“轮流报数"的分工游戏。
假设我们现在启动了4个线程来跑这段代码（线程号分别是0,1,2,3）：
由于外面只有 #pragma omp paraLlel 而没有 for，这4个线程每人都完整地把 i 从O循环到
了1048576。但是因为if的存在，它们开始挑食了：
0线程0跑循环时：只有当i%4==θ时才动手（处理i=0，4，8，12...）。
0线程1跑循环时：只有当i%4==1时才动手（处理i=1，5，9，13...）。
o线程2跑循环时：只有当i%4==2时才动手（处理i=2，6，10，14...）。
0线程3跑循环时：只有当i%4==3时才动手（处理i=3，7，11，15...）。
结果：它们完美错开，各做各的，谁也不抢谁的。当4个线程都把循环跑完后，整个数组的所有元
素也恰好都被取反了一次。所以结果是完全正确的。


原因一：空转开销 (浪费CPU算力)
o正常单线程：循环100多万次，做了100多万次取反。
这个多线程：4个线程每个人都循环了100多万次（总共循环了400多万次！）。虽然大部分
时候被if 挡住了没做取反，但i++、判断i<1048576、算i%4 这些控制代码，4个
线程都在老老实实地算。这种空转极大地浪费了时间。
原因二：伪共享（False Sharing）－－致命一击
这是多核编程里著名的“打架"现象。
计算机在读写内存时，是以一个“缓存行（CacheLine，通常是64字节）”为大单位一起读进CPU
核心里的。
一个64字节的缓存行，刚好能放下16个int 类型的数组元素（比如A[θ］到A[15]）。
线程0把包含A[θ]~A[15]的这块内存读进了自己核心的L1缓存，高高兴兴地把A[θ]改成了-A[0]。
2就在同一时刻，线程1也要改A[1]。但因为A[1]和A[θ]在同一个缓存行里，根据硬件的
一致性规则：线程0修改了这一行，就导致线程1手里的这一行数据“失效"了！
3线程1发现失效了，气哄哄地拍桌子，被迫重新去慢得要死的主内存（或者L3缓存）里重新拉
取最新的数据。
4线程1刚拉完数据把A[1]改了，结果又导致线程0的缓存失效了.
这4个线程因为是交错分工的（0号、1号、2号、3号紧挨着），导致它们在运行过程中，疯狂地把
隔壁线程的缓存行给“弄脏/弄失效”。CPU的核心们几乎没心思算取反了，大把的时间都浪费在“你的
缓存失效了，去内存重读吧”、“我的也失效了，我也去重读"的内耗中。
这就是Coherence Miss（一致性缺失）

代码的意思是根据总的线程的数量，把i均分给他们线程的序号，等轮到哪个线程了，就把那个线程
对应的A[序号]变为负数，#pragma omp parallel则正好运行线程次下面的代码，所以相当于：
i从0到1048576，每个线程都运行一次，直到属于自己序号再取反，空访问再加上Coherence Miss，
缓存行也会经常miss，所以非常慢，不如单线程串行


Q1.9：为什么选(b)正确但比串行慢？ (你选了c)
#pragma omp parallel for
for (int i = 0;i< 1048576;i++){
	#pragmaomp critical//互斥锁（临界区)
	sum += A[i];
}
原理解析：
你注意到了 #pragma omp critical 可以解决Q1.8的数据竞争问题，这很棒！它的确保证了
同一时间只有一个线程能去执行sum+=A[i]，所以结果必定正确。
为什么慢？
critical是一个重量级的互斥锁。
代码里，这个锁被放在了最内层循环一一这意味着，在100多万次循环里，每一次加法都要经
历：申请锁→加法→释放锁。
当线程A在加法时，线程B、C、D全都在门口傻傻地排队等候。原本并行的程序，被这把锁
硬生生地逼成了“单列纵队"单线程运行。更糟糕的是，多线程频繁申请/释放锁的开销(Overhead）极大。
结论：结果正确，但由于严重的锁竞争和开销，速度远慢于普通单线程，选(b)。
注：Q1.10展示了正确做法一一先在私有草稿纸上累加（private_sum），最后整个线程跑完
了，才出门用critical锁一次，这就飞快。

这里的目的是，先把求和拆成n线程份，然后再把这些份数用锁求和，如果直接每次小循环都加了锁
那就还不如不并行

Q1.10:
int A[1048576];
initializedata(&A);
int sum = 0;
#pragma omp parallel
{
	int private_sum = 0;
	#pragma omp for
	for (int i = 0; i  1048576; i++){
		private_sum += A[i];
	}
	#pragma omp critical
	sum += private_sum;
}

在C/C++中，变量的生命周期是由它所在的大括号决定的。
你的 private_sum 是在 #pragma omp parallel 的大括号内部声明的。这意味着:
o在并行大括号内部：每个线程都有一个属于自己的private_sum。
o一旦出了并行大括号：这些private_sum 就全部死亡并被销毁了。
当程序运行到最外层的sum+=private_sum；时，编译器甚至会直接报错："error:
‘private_sum’wasnotdeclaredinthisscope"。因为在串行主线程看来，大括号外压根不
存在一个叫private_sum 的变量。
我们假设一个更极端的场景：如果private_sum是声明在最外面的（假设它是一个数组或者通过
某种方式在外面能访问到）。
由于sum += private_sum；被你写在了 #pragma omp parallel 的大括号外面，这意味着并行
区域已经结束了，程序已经退回到了单线程（主线程）状态。
原本的Q1.10：每一个线程在自己并行的生命周期结束前，都老老实实地排队（critical）
把自己的草稿纸加到了总分sum里。
你修改后的代码：8个线程在里面热火朝天地算完，大括号一闭，7个线程原地解散。只剩下主
线程（Thread O）孤零零地走出来，执行了一次 sum+= private_sum；。它只能加上主线程
自己那张草稿纸上的数，其余7个线程付出的汗水全部蒸发了。
