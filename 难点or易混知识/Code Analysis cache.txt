Given the follow chunk of code, analyze the hit rate given that we have a byte-
addressed computer with a total memory of 1 MiB. It also features a 16 KiB
Direct-Mapped cache with 1 KiB blocks. Assume that your cache begins cold.
#define NUM_INTS 8192 // 2ˆ13
int A[NUM_INTS]; // A lives at 0x10000
int i, total = 0;
for (i = 0; i < NUM_INTS; i += 128) {
	A[i] = i; // Line 1
}
for (i = 0; i < NUM_INTS; i += 128) {
	total += A[i]; // Line 2
}

这里block是10位，即2^10-1=1023byte，一个int是4byte，每次跳128个数，即512byte
所以每个block被访问两次，第一次miss，第二次命中
计算标记为“第 1 行”的行的缓存命中率：
整数访问间隔为 4 * 128 = 512 字节，这意味着每个块有 2 次访问。
每个块中的第一次访问是强制缓存未命中，但第二次访问命中，
因为 A[i] 和 A[i+128] 位于同一个缓存块中。因此，最终命中率为 50%。

总结Line2的逻辑：
1.数组太大：数组32KiB，缓存只有16 KiB。
2.缓存被顶替：Line1执行完时，缓存里装的是数组的后半段（16K到32K的数据）。
3.重新开始：Line2从A[0]开始读，而A[0]早就被顶替掉了，所以Line2必须从头开始
发生强制未命中。
4.不看total：因为total在寄存器里，不产生缓存访问。
因此，Line2的表现和Line1完全一样：每两个int访问里，一个Miss，一个Hit。

数组在内存里占了多大的地方。

代码里写的是total+=A[i]。如果编译器很"笨"，它每次都会：
1．去内存/缓存里把total读出来。
2.加上A[]。
3．再把结果写回内存/缓存里的total地址。
但现代编译器（Compiler）很聪明。它发现total是一个在循环里被频繁更新的局部变量。它会
直接给total分配一个寄存器。
在整个循环期间，total的值都留在CPU寄存器里加加减减。
只有当循环彻底结束后，它才会把最终结果写回内存。
